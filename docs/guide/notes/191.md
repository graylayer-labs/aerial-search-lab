# #188 and #191 Send frozen-head training to a CPU cloud job

Set out to: give the AWS account real, small use while it decides on the GPU quota, by sending `train-head` to ml.m5.xlarge on spot (owner: "approve cpu jobs", 2026-10-23; at most 2 h a job, EUR 5 a month).
Chose: a new command, `sagemaker-train-head`, owned by the frozen-head project, over an `--instance` flag on the detector's `sagemaker-train`; `shared/` gained only a priced instance allow-list and an instance and command on the launcher. One camera's cached features (14,844 files) go to S3 under their content hash, and the job checks that hash before it trains.
Expected before running: a launcher change, with the cache upload a small follow-up.
Surprising:
- Hashing read every file into memory, which was fine for manifests and would not fit 5.5 GB on the job's machine. A 1 MiB streaming hash gives the same digests.
- The attestation passed SageMaker's 512-character limit per variable by one character once the features hash was added, so the hash travels in its own variable and the job folds it in.
- Review found that `sagemaker-fetch` checked a run's commit only when its `run.json` sat at the top of the job's output. Real outputs are flat, but a nested, forged record would have been copied in unchecked. Every record is now checked, at any depth.
- One mutation survived the fix (checking only top-level runs), although every line was covered. A test now pins it: coverage shows a line ran, and only a mutation shows a test would notice it breaking.
- The EUR 5 cap reads only m5 usage from Cost Explorer. If AWS spells usage types differently than expected, it refuses instead of reading zero.
Sources: PRs #190, #192, #197 to #200; a dry run on main bd1853c (EUR 0.12 estimate, EUR 0.49 worst case); docs/decisions.md lines dated 2026-10-24.
